# Upgrading to 0.3.0

These notes are for servers and admin workstations that run 0.2.x (0.2.6 or
earlier). Follow the [general upgrade steps](README.md). This page lists
only what is specific to 0.3.0: the server
and workstation steps that the general steps refer to, and what behaves
differently afterwards.

The commands assume the default hosting account `git` with the home
directory `/home/git`. If you installed with `--git-user`, use that account
instead.

## What changes in 0.3.0

Fixes:

- `install --default-branch NAME` put `gitolite-admin` on branch `NAME`.
  Gitolite 3.6.12 (Debian 13) only applies pushes to `master` of
  `gitolite-admin`, so every admin change was silently ignored.
- `backup` failed for every repository when run as root ("detected dubious
  ownership").
- `install` stopped halfway when it was started from a directory the hosting
  account cannot read, such as `/root`.
- `doctor` hung, or passed without checking anything, when its input was not
  a terminal.
- Running `install` again on an installed server was refused, but only after
  it had already rewritten the sshd port drop-in with the new `--ssh-port`.
  It now stops before changing anything.
- `install` failed at its last step when systemd was not running (for
  example in a container). It now warns that sshd has to be reloaded by hand.
- `status` always reported `Gitolite: missing`, and without root it showed
  wrong values (for example `Repository count: 0`) without saying so. It now
  shows the Gitolite version, and without root it warns and shows
  `(needs root)` for the fields that only root can read.

New commands and options:

| Command or option | Purpose |
|---|---|
| `sync` | Update `gitolite-admin` from `origin`, keeping staged changes |
| `host-keys` | Print SSH host key fingerprints and `known_hosts` lines |
| `ssh-limits`, `install --max-startups` | Show or set sshd's `MaxStartups`, for many agents connecting at once |
| `agent-branches` | In a project clone: list agent branches, ahead/behind the default branch |
| `share` | Serve an archive of a branch or tag at a temporary random URL, for a one-off deploy to a machine without a key ([One-off deploys](../share.md)). Needs `python3` on the machine that runs it, and `openssl` for `--tls` |
| `group-set`, `group-remove`, `group-list` | Manage Gitolite groups such as `@agents` |
| `repo-set --agent-rewind` | Let agents force-push and delete their own branches only |
| `user-remove --all`, `--force` | Remove every key of a user; allow removing the last admin key |

Access rules that `repo-set` now writes:

- Only the owner can push tags. Writers and agents cannot create, move or
  delete tags.
- Writers cannot write to `agent/*` branches; those are reserved for agents.

Existing ACLs keep their old rules until they are written again with
`repo-set` (workstation step 2 below).

New installs also accept `GIT_PROTOCOL` in sshd (Git protocol v2) and keep a
reflog in every hosted repository. An existing server needs the manual
steps below for both.

## Server steps

Do these after the backup and the first `doctor` run of the general steps.

1. **Repair `gitolite-admin` if it is on the wrong branch.** If `doctor`
   reports `gitolite-admin HEAD is 'refs/heads/...', expected
   refs/heads/master`, the server was installed with `--default-branch`, and
   Gitolite has been ignoring every admin change since then. Repair this
   first, following
   [Repair an admin repository on the wrong branch](../administration.md#repair-an-admin-repository-on-the-wrong-branch).
   The later workstation steps need it.
2. **Keep a reflog in every hosted repository**, so force-pushed commits can
   be recovered (`doctor`: `hosted repositories keep no reflog`):

   ```bash
   sudo runuser -u git -- git -C /home/git config --global core.logAllRefUpdates always
   ```

3. **Let Git clients use protocol v2** (`doctor`: `sshd does not accept
   GIT_PROTOCOL`). This adds `AcceptEnv GIT_PROTOCOL` to the
   `Match User git` block of the drop-in written by 0.2.x. It only adds the
   line when it is missing, so it is safe to run again:

   ```bash
   sudo grep -qx '    AcceptEnv GIT_PROTOCOL' /etc/ssh/sshd_config.d/90-gitolite.conf \
     || sudo sed -i '/^    PermitTTY no$/a\    AcceptEnv GIT_PROTOCOL' /etc/ssh/sshd_config.d/90-gitolite.conf
   ```

   Then check the SSH configuration and reload sshd:

   ```bash
   sudo sshd -t && sudo systemctl reload ssh
   ```

   If you edited that drop-in by hand, add the line inside the
   `Match User git` block yourself instead.
4. **Keep the new backup.** Backups made by 0.2.x as root most likely
   contain no usable repository mirrors, so the backup from the general
   steps is probably your first complete one.
5. **Distribute the host keys.** Print them and add the `known_hosts` lines
   to admin workstations and agent hosts (see
   [Server host keys](../install.md#server-host-keys)):

   ```bash
   sudo ./mini-git-server.sh host-keys --host git.example.internal
   ```

When you run `doctor` again, the admin branch, reflog and `GIT_PROTOCOL`
checks should be `[ OK ]`.

## Workstation steps

Do these on **one** admin workstation, after `sync`. The other workstations
get the result with `sync`.

1. **Enable script-managed groups.** `admin-init` adds
   `include "groups/*.conf"` in front of the existing
   `include "repos/*.conf"` (Gitolite needs a group to be defined before a
   rule uses it):

   ```bash
   /path/to/mini-git-server.sh admin-init
   /path/to/mini-git-server.sh apply -m "Enable script-managed groups"
   ```

2. **Rewrite the existing repository ACLs with the new rules and checks.**
   For each repository under `conf/repos/`, run `repo-show` and then the
   reapply command it prints:

   ```bash
   /path/to/mini-git-server.sh repo-show --repo project-x
   ```

   Then review the staged diff and `apply` it. What to expect:

   - Every ACL with writers or agents gets the new deny rules for tags
     (`- refs/tags/`) and, with writers, for agent branches (`- agent/`).
     This takes tag pushing away from writers and agents. If a writer used
     to push release tags, the owner has to do that from now on.
   - `repo-set` refuses an identity with two roles (for example an agent
     that is also a writer, which could push to every unprotected branch)
     and warns about identities without a key.
   - If your daily identity is also the admin identity, as in the examples
     before 0.3.0 (`install --admin-name arthur`, then `--owner arthur`),
     `repo-set` warns `'arthur' is also a gitolite-admin identity` for every
     repository. The ACL is still written. The warning stops once admin
     rights are moved to a separate identity (see
     [Optional changes](#optional-changes)).
   - An ACL with only an owner and readers does not change.
   - Fragments written by very old 0.2.x versions, without the
     `# mini-git-server:` metadata lines, also get those lines added.

## Optional changes

These change how you work, so do them when convenient:

- Move admin rights from your daily identity to a separate admin identity:
  [Moving admin rights to a separate identity](../identities.md#moving-admin-rights-to-a-separate-identity).
- Put your agents in a group and use `--agents @agents`, so a new agent only
  needs `group-set`: [Groups](../access-control.md#groups).
- Let agents rewrite their own branches with `--agent-rewind`:
  [Letting agents rewrite their own branches](../agents.md#letting-agents-rewrite-their-own-branches).
- Add the agent instructions template to your project repositories:
  [Instructions for the agents](../agents.md#instructions-for-the-agents).

## What behaves differently

Check scripts and habits that use these commands:

- `apply` only runs on the `master` branch of `gitolite-admin`, and stops
  before committing when another machine has pushed newer changes. Run
  `sync`, then `apply` again
  ([Working from several machines](../administration.md#working-from-several-machines)).
- `repo-set` refuses an identity with two roles, and agent names that contain
  characters other than letters, digits, `-` and `_`.
- ACLs written by `repo-set` let only the owner push tags, and keep writers
  out of `agent/*` branches.
- `user-add` refuses a name like `arthur@laptop` (Gitolite reads it as
  `arthur`; use `--key-id laptop`), and a key that is already stored for
  another identity.
- `user-remove` refuses to remove the last key that can push to
  `gitolite-admin`, unless `--force` is given.
- `user-add` and `repo-set` warn when an identity that can push to
  `gitolite-admin` gets another key or is used in a repository ACL.
- `status` warns when it is not run as root and then shows `(needs root)`
  instead of the values it cannot read. It also has a new `SSH MaxStartups`
  line. Check scripts that read its output.
- `backup` works when run as root.
- `doctor` checks `authorized_keys` correctly when its input is not a
  terminal (for example from cron or over `ssh`), and has new checks for the
  admin branch, the reflog and `GIT_PROTOCOL`.
